## 第 3 页：回答了哪些问题？（60 秒）

“我们重点服务负责 HNSW 建索引与调参的数据库工程师和 DBA，检索平台工程师参与召回和延迟验证。这类困难有公开依据：上游文档的 HNSW 阶段比较粗，内存不足会影响构建速度，提高搜索参数也会带来速度代价。2026 年还有用户询问，为什么增加内存预算后收益不明显。我们据此聚焦三个问题：慢在哪里、该怎样调整、调整后是否有效，用阶段计时、参数对照和查询验证提供判断依据。”

公开依据见 [S16：pgvector v0.8.6 官方 README](https://github.com/pgvector/pgvector/blob/v0.8.6/README.md#hnsw) 和 [S17：Issue #969](https://github.com/pgvector/pgvector/issues/969)。README 证明基线版本的机制与权衡仍需使用者处理；“粗粒度进度难定位具体耗时”是据此作出的诊断需求判断。#969 于 2026-03-15 发起，提问者使用 0.8.2，当前已关闭，仅作为真实调参疑问的例子，不当作 0.8.6 尚未修复的缺陷，也不据此声称问题普遍或本文工具能解决该用户的具体环境。

三条路径的具体依据：上游 HNSW 文档只列 `initializing` 和 `loading tuples` 两类阶段；图超出 `maintenance_work_mem` 后构建会变慢；提高 `ef_search` 可以改善召回，同时付出速度代价。#969 的用户曾增加内存预算但未见明显收益，因此复验必须保留实际负载和资源约束，不能保证“增加内存必然显著加速”。这些详细说明保留在讲稿，页上只保留问题短语及出处。

异常验证是三条使用路径的共同基础。六类原始要求的详细对应关系留作核对，不在现场逐条念：

- 构建耗时：内部八段计时与瓶颈解释；证据为时间线校验及全量 GloVe spill 报告，见 S3、S5。
- 内存与规模：spill 上下文和资源采样；行数、维度、m 的控制变量，以及全量 GloVe 两档预算对照，见 S5、S14。
- 低召回风险：Recall 检查与阈值提示；独立验证查询的平均结果为 91.13% → 95.47%，见 S6。
- 参数建议：条件式建议及收益、代价对照；覆盖构建内存、索引参数和查询选参，见 S5、S6、S14。
- 进度观察：四类阶段、串并行发布以及已有任务只读接入；本地观察 11 / 11 检查，见 S2–S4。
- 异常验证：TAP / SQL 与工具异常处理；失败、取消、非法参数和重复构建，见 S3、S14。

行数、维度、m 的控制变量来自早期独立规模实验，不能说此次全量 GloVe 同时扫描了所有参数。这是本地已有实现与证据，不表示活动方逐项验收通过。性能 5% 和平均 Recall 95% 均为自设参考，维护者 Review、最终集成和正式提交仍未完成。

### 终端 A：按记录参数整理的完整命令

在完整项目根目录运行，需预先准备记录中的普通 timing-v1-arm64 镜像，55432 端口空闲。此命令创建自己的隔离测试实例并在结束后清理，不用于已有业务库。

```sh
python3 experiments/hnsw_build/run.py \
  --isolated --image opentenbase-pg18-pgvector:timing-v1-arm64 \
  --build-timing --rows 50000 --dimensions 64 \
  --maintenance-work-mem 8MB \
  --m 16 --ef-construction 64 --parallel-workers 0 \
  --seed 0.42 --sample-interval 0.5 \
  --statement-timeout-ms 300000 --label manual-low
```

复验时只将 `--maintenance-work-mem 8MB` 改为 `--maintenance-work-mem 64MB`，用 `--label manual-high` 区分输出目录。标签不改变负载。此次比较没有开启召回查询，不据此讲召回质量改善。

### 终端 B：运行时可选的进度查询

先从 `docker ps` 找到本次 `hnswdiag-...-db-1` 容器，将下面的 `<本次隔离容器名>` 替换成该实际名称。查询属于使用者另开终端执行的 SQL，不是 Python 工具自动展示的窗口。

```sh
docker exec <本次隔离容器名> \
  psql -X -U postgres -d postgres -P pager=off \
  -c 'SELECT phase, tuples_done FROM pg_stat_progress_create_index;' \
  -c '\watch 1'
```

没有进度行不单独证明构建成功；完成状态和内部计时需看构建方报告。短阶段可能被轮询漏掉，本次低内存采样只观察到内存构建和磁盘插入，但内部计时包含 flush / WAL。来源 S15。

## 第 6 页：两个工程难点（75 秒）

“第一个难点是并行可见性。worker 对当前 backend 的进度更新，不能替代 leader 对使用者发布状态。因此通过共享阶段协调，再由 leader 发布，并保证阶段只向前推进。第二个难点是计时可靠性：轮询会漏掉短阶段，共享内存释放后也不能再读取计时，所以记录边界，并在释放 DSM 前复制所需信息。”

分别按问题、设计、验证讲。默认关闭的 `hnsw.build_timing` 开启后按边界读时钟，没有逐向量增加时钟读取。可选区间未发生时记为 null / N/A；失败或取消不输出 complete 摘要，不能把部分数据拼成一次成功构建。

对外四类阶段是内存构建、图写成索引页、磁盘路径插入、WAL。内部八段按顺序是 setup、memory_build、spill_drain、flush、disk_insert、finalize、wal、cleanup。两种粒度不逐项对应；计时是一个 leader 时间线，不是 worker CPU 求和，也不是整个 CREATE INDEX 事务提交延迟。`flush` 是图页面物化，不是设备 fsync 耗时。来源 S2–S3。

如希望补充约 30 秒的工程决策复盘，可讲既有测试修正：最初新增 TAP 错误假定新建索引必定写 WAL；核对数据库行为后，明确测试 WAL 模式并保留 unlogged 路径的 N/A 检查，没有为满足测试而修改数据库 WAL 决策。该经历有失败日志和修正记录支撑，不应编成未验证的个人能力评价。

## 第 8 页：案例一：定位主要耗时（35 秒）

“这是 118 万条 100 维 GloVe 向量、1024MB 构建预算的一次实际运行。内存阶段约 421.5 秒，图写成索引页约 6.37 秒，后续磁盘路径插入约 982 秒，占内部总时间 69.4%。诊断让我们可以区分这两个原本容易混淆的落盘相关区间。”

横轴为内部累计时间。沿一条横向时间线从左向右讲内存构建、图写成索引页、磁盘路径插入和 WAL；全部八段的宽度按原始耗时累计，四个主要区间直接标注，其余合计约 0.068 秒。短的 flush / WAL 用引线标注，条宽没有人为放大。深蓝色长段突出磁盘插入占 69.4%。

内部总时间 1414.450097 秒与完整命令 1414.648555 秒分别报告。这不是 worker CPU 求和，磁盘路径也包含扫描与等待，不能据此断定 SSD 是唯一瓶颈。低内存三次的磁盘路径占比分别为 69.4%、76.8%、79.7%；本页只展示第一次。来源 S5。

## 第 9 页：内存建议复验（60 秒）

“我们固定同一数据、索引参数和实际 worker 数，每档各做三次。1024MB 三次都 spill，1792MB 三次均无 spill。完整构建中位数从 1414.6 秒降到 326.6 秒，约减少 76.9%，但容器近似峰值中位数也从 2781.1MiB 增至 3580.7MiB。”

这项收益归属于内存参数调整。诊断的贡献是帮助定位并验证建议，不能说 C 补丁让算法提速 4.33 倍。只有资源余量允许时才考虑类似调整，本机结果不能自动变成生产配置建议。来源 S5。

先看左图全部六次运行，可看到同一档内部仍有波动；浅色条表示中位数，范围和 spill 次数直接标在该预算行。纵向错位仅为避免点重叠，没有绘制置信区间。再按相同预算行看右图：容器峰值中位数增加约 28.8%。两图一个用秒、一个用 MiB，不能直接用条长相除。这样同时解释约 76.9% 的耗时减少与资源代价。

## 第 10 页：低召回风险与调整代价（60 秒）

“与构建耗时问题对应，另一个原始要求是低召回风险检测。第二个案例先确认是否达到自设质量目标，再同时呈现提高查询参数后的质量改善与时间代价。”

“第二个案例检查索引能查询之后，质量是否足够。锁定新的最终索引后，用不参与选参的 1000 个新验证查询比较两个 ef_search。平均 Recall@10 从 91.13% 到 95.47%，同时 p50 从 3.74ms 到约 29ms，约为原来的 7.75 倍。”

Recall@10 是返回 10 个 ID 与精确 Top-10 的重合比例。95% 是我们设的平均目标，不是官方标准，也不是每个查询保证。耗时为暖缓存服务器执行时间，没有包含业务网络、完整应用链路，也没有生产并发负载。来源 S6。

散点图向上表示平均召回增加，向右表示查询耗时增加。两个点只代表两个已测配置，不能顺着它们推断其他参数的连续变化或最优点。

左图点旁直接标出参数、召回与 p50。右图按 p50、p95 两行分别放置两种配置的数值，蓝色圆点是 ef=400，红色方点是 ef=1000；同一毫秒刻度从零起计，点旁保留精确到两位小数的数值。由横向位置直接比较延迟代价，不把两组配置画成置信区间或连续参数曲线。

这轮使用新建的最终索引；不要把 9/9 内存报告中的旧召回结果混入，也不要推断加大构建内存会提高召回。

## 第 17 页：附录 B：正式性能方法

沿四个步骤解释统一构建、固定执行顺序、面板内聚合与联合判定。最后一框写的是“均须低于自设 5%”，是预定的判定要求，不是已通过的结果。

面板内每条件两次测量先取几何均值，再求相对于原版的比值。每项有 24 个面板统计单位，不是 48 个独立样本。正逆序平衡执行位置，统一编译工具链控制版本构建差异。

主判定用精确二项顺序统计量形成中位数上界，并用 Bonferroni 处理 12 项比较。参考线严格小于 5%。既有中断批、旧 A/A 失败仍保留，新正式批使用另立的事前固定方法。

这种方法仍依赖独立可比等假设，不能消除所有系统噪声。不能按结果删除慢样本、将原始测量混批，或反复加样本直到过线。来源 S7。

## 常见追问

**贡献在哪里，是否只是给原有功能换名字？**

新增的是构建路径细分、并行发布协调、spill 上下文、可选可靠内部计时，以及把这些证据接到只读观察和可复验报告。HNSW 算法、原有 spill 行为和原有进度视图属于上游。

**为什么测试都过了，还说性能未完全证明？**

功能测试检查行为，性能对照检查代价。前者通过不推出后者的统计上界已低于门槛。

**既然计时默认关闭，是否可以声称没有开销？**

不能。关闭计时避免相应计时工作，但候选仍包含阶段等变更。正式对照单独比较关闭模式，其中并行无 spill 的低于 5% 支持仍未建立。

**是否需要现在把三个性能问题全部解决？**

当前没有确认的项目方硬门槛，也没有已定位的必修 C 缺陷。建议先确认接收标准，以已实现功能和诚实限制进入 Review。如对方要求严格开销保证，再约定新的验证方案。

**这些结果会怎样改善业务？**

现有证据支持诊断信息更具体、参数建议可复验和收益代价同时呈现。减少排障工时或改善业务 SLA 是预期价值，尚未通过真实业务库量化。
