# OpenTenBase HNSW 构建诊断一页说明

## 项目状态

腾讯犀牛鸟 OpenTenBase 项目，固定为 OpenTenBase 18.6 `REL_18_STABLE` + 外置
pgvector 0.8.6。C 诊断/内部计时、只读观察及有限验证已实现并完成本轮实验，
后续有界定位确认旧开销协议有顺序混杂，新对照仍波动较大，性能验收未关闭。
9/11 又完成统一构建、98 项工具测试和常规版 20 项功能检查，补上供电/双时钟保护。
9/12复核新增窗口结果后，三个完整A/A分别有3/4、0/4、0/4场景通过；最后一次
接电且负载明显降低仍有波动，按原规则未启动正式对照。不再重复要求空闲窗口，
下一步先Review测量方案；“诊断总开销低于5%”仍未得到证明。
没有已归因且待修复的C缺陷，不无界追加实验。本人及维护者 Review、
正式交付未完成。本轮不推送、不改上游。
Debian ARM64 Docker 做实验，OrbStack CentOS Stream 9 ARM64 补充 C 兼容性。

## 问题

向量索引构建由内存路径转入磁盘路径后，运维人员很难仅凭笼统进度判断慢在哪、
是否还在推进、该不该增加内存。索引建成也不意味着召回率满足检索要求。
本项目解决的是“可定位、可解释、能复验”的工程问题，不是重新发明索引算法。

## 方案

1. 公开四个细分阶段；并行进程共享状态、leader 发布；spill 告警补充图内存与参数。
2. 默认关闭的内部计时记录八段边界，区分排空等待、图写入与剩余磁盘插入，
   弥补定时采样漏掉短阶段的问题。
3. 独立只读工具连接已有任务，报告阶段、等待与采样停滞；不读业务向量、不写库、
   不取消构建；任务消失不自动判成功。
4. 用可复现实验检查内存调整是否有效；用独立验证查询检查召回与延迟代价。
   保留失败与未达标，不把“程序跑完”当成“业务目标已满足”。

## 验证

| 门槛 | 结果 |
|---|---|
| C 候选与两环境兼容性（9/6） | Debian/CentOS 各 28 个 HNSW TAP 文件、632 断言、4 项 SQL regression，通过；本轮未改 C，未重跑这批测试 |
| Python 工具（9/11） | 完整环境 98/98；无可选依赖时 92 通过、6 skip |
| 只读观察（9/10） | 本地真实受限账号 11 项检查；尚未连接真实业务数据库 |
| GloVe 内存案例（首轮） | 全量 1,183,514×100；两档各三次，1024MB 均 spill，1792MB 均无 spill；构建中位数 1414.649s → 326.571s |
| GloVe 有限召回（新轮） | m16/efc128/ef1000，新 1000 查询平均 Recall@10=95.47%；查询 p50/p95=29.00/44.95ms。同索引 ef400 是91.13%、3.74/7.13ms，收益有明显代价 |
| 计时/观察成本（前轮） | 192 次正式 + 96 次预热；存在版本/执行位置/前项混杂，原比值不能独立证明各功能纯成本 |
| 默认关闭有界定位（前轮） | 另108次正式+72次预热、六种排列；位置匹配后串行spill/并行无spill中位差异+0.49%/+3.29%，但上界+72.08%/+11.94%，仍未证明低于5% |
| 总成本验收（最新） | 同一编译环境重建原版/候选四镜像；常规版16次构建、20项功能检查通过。三个完整A/A均未整体通过，正式原版/诊断对照未启动，性能尚未验收 |

内存调整的收益不是 C 补丁提速。内部计时定位时间区间，不直接证明 SSD 或 CPU
是根因；本机成本不外推到生产，也不保证零开销。公开词向量不等于真实业务数据。

## 现场演示顺序

1. 用小规模 spill 构建展示细分进度与内部阶段时间，解释慢主要发生在哪段；
2. 展示 GloVe 两档内存的三次重复，说明调整建议如何复验；
3. 用只读报告展示等待与中途接入，说明为何任务结束仍需构建方确认结果；
4. 展示独立召回验证与查询代价，最后说明测试、开销及业务边界。

## 贡献边界

组内图式 ANNS、内存预算与 SSD 研究提供问题背景；本项目将其落到数据库构建
可观测性、可重复测试和有边界的调参验证。李莲鑫是师兄，具体启发按事实致谢；
没有已核实的组内成熟代码移植。不声称发明 HNSW、实现分布式优化或证明生产收益。
本人仍需理解并复现 AI 辅助完成的实现，不能把自动测试当成自己已掌握或维护者已签字。

## 剩余工作

1. Review已有开销证据、A/A准入与配对设计；确认窗口后的复验仍未通过，不自动重跑。若方法需调整，先明确新协议与执行预算，不静默放宽门槛或盲目修C；
2. 本人/维护者 Review，并确认目标代码放置方式与交付入口；
3. 按最终接收形态 clean rebuild 后，再由用户决定提交；真实业务接入另需明确连接与权限。
