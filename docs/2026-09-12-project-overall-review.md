## 1. 先给出整个项目的结论

我们做的是：**在 OpenTenBase PG18 上，为 pgvector 的 HNSW 索引补充构建诊断能力，让使用者能知道慢在哪、有没有发生内存不足后的路径切换，并通过参数调整和复验判断建议是否有效。**

项目约定的功能候选开发和用户选择的本地试用验证已完成，包括阶段细分、内部计时、只读观察、诊断报告、参数与召回验证、自动测试和两个公开向量案例。没有新增必做功能，也没有已发现而未修复的具体产品C缺陷。

但目前还不能说“所有工作和验收全部完成”：

- 已约定的核心功能已经实现，没有一批尚未开始编写的核心功能。
- 完整正式对照的9/12项支持低于自设5%参考线，三项并行条件仍缺支持；新增构建时长校准及独立审计已完成，不替代正式判定。
- 你已确认本人 Review 完成；活动方接受个人仓库链接，仓库整理、最小复现与实际提交继续推进，维护者反馈尚待进行。
- 个人私有仓库已经初始化，不等于已经向 OpenTenBase 交付或合入。

因此，当前准确状态是：**约定功能候选与本地试用验证已完成，整体性能验收与正式交付未关闭。**补充校准及清理也已经独立核验。若没有实质改善验证条件的可检验干预或具体缺陷，就保留三项性能限制并收口，不自动加大实验规模或改C。

## 2. 最初的任务、目标用户和价值

### 2.1 项目方原本要求什么

启动会提供三类题目，我们选的是**项目二：向量索引构建与诊断增强**，不是项目一的查询性能优化，也不是项目三的图查询优化。

项目二要求围绕大规模向量索引构建体验，关注构建耗时、内存占用、低召回风险、参数推荐、进度和异常测试。诊断要说明问题、原因、调整方法和验证方式；交付包括代码改进、诊断 SQL／工具、TAP 或回归测试、调参说明。

统一边界是 PG18／PG19、集中式 Linux 场景，推荐 CentOS；结果须说明环境、规模、参数、重复次数和统计口径，并提供复现工具。OpenTenBase 的分布式能力是平台背景，**不意味着本题要求我们开发分布式向量索引**。

依据：启动会 PDF（作者本地留档）物理第 3、6、7、11、12 页；会议逐字稿（作者本地留档）的 `00:03:03`、`00:08:37–00:10:53`、`00:13:53–00:14:49`。PDF 中第 6、7 物理页的印刷页码顺序相反，查阅时以标题为准。

下面几件事是后续选择，不能冒充项目方原始硬要求：

- 选 HNSW、OpenTenBase 18.6 和外置 pgvector 0.8.6，是本地实现方案。
- 平均 Recall@10 达到 95%，是我们这轮案例的自设目标，不是通用合格线。
- 诊断开销低于 5%，是后续验证采用的自设参考线，不是已确认的官方接收标准。
- GloVe 是我们选用的公开评测数据。会议没有给项目二指定某个“官方数据集”；逐字稿中“尽量使用官方数据集”的发言出现在项目三讨论中。
- 没有要求必须实现 AI／LLM 诊断助手；会议举过这种实现思路，我们采用的是规则、证据和复验工具。

### 2.2 我们面向谁

以下是项目的目标用户定位，不是已经完成客户访谈或生产部署的声明。

| 目标用户 | 具体困难 | 本项目提供的帮助 |
|---|---|---|
| 负责向量库建索引、重建索引的数据库工程师／DBA | 任务很慢，笼统进度看不出正在做什么；不知道是否该继续等或调整配置 | 细分阶段、spill 上下文和内部耗时，给出可追查的证据 |
| 使用向量检索的知识库／检索平台工程师 | 索引能查询，却不知道召回是否够用；提高参数可能让查询更慢 | Recall@K 验证、参数对照，同时展示质量收益与时间代价 |
| 插件维护者及问题复现人员 | 用户说“构建慢”，但日志缺配置，结果难复现 | 版本、参数、环境、日志、测试与复现入口一起留存 |

主要服务的是数据库和检索基础设施人员，不是直接面向知识库终端用户的产品界面。

### 2.3 我们实际解决的是哪一层问题

上游原本就有 HNSW 建图、spill、进度视图和内存不足告警。我们的贡献不是重新发明这些功能，而是把它们之间缺少的诊断信息补起来：

**看到任务慢 → 分辨构建路径与耗时区间 → 结合参数和资源提出调整 → 用同负载复验 → 同时检查检索质量与代价。**

已经有本地证据的价值，是诊断信息更具体、参数建议能够被验证、未达标结果不会被误报为成功。减少排障工时、减少盲目重建、缩短业务上线时间，是合理的预期收益，**尚未在真实业务中量化**。

## 4. 按真实推进顺序：每个阶段为什么做、完成了什么

### 阶段一：理解项目并选题｜启动会后至9/2前

本地会议文件名及PDF生成日期对应8/25；早期沟通的逐条日期不据此倒推。

**当时的问题：**你已入围，但不熟悉题目；希望与研究生组内的向量数据库方向连接，同时避免依赖难以使用的组内 Linux 服务器。

**当时决定：**选“索引构建与诊断”，从 HNSW 的构建过程入手。cyrilwu 后续通知可选社区同步的 PG18／PG19 分支，我们实际选定 PG18。Mac 作为工作机，数据库运行于 Linux 环境；先本地开发和测试，最终再确认交付方式。

**形成的范围：**OpenTenBase 18.6 `REL_18_STABLE` + pgvector 0.8.6；不同时做 IVFFlat、图查询、分布式优化或新 ANN 算法。早期逐条讨论的确切日期不补写。

### 阶段二：环境和第一版诊断闭环｜9/2

**原计划：**先跑通基线，找到一个小而有效的切口。

**实际完成：**在 Apple M4、24GB 内存的 Mac 上，以 OrbStack 的 Debian ARM64 Docker 环境源码编译、启动数据库与扩展，验证 HNSW 建索引和查询；随后完成第一版 C 改动及诊断脚本。

- 把笼统的 `loading tuples` 细化为内存构建、图写成索引页、磁盘路径插入、WAL 写入四类阶段。
- 并行 worker 更新共享阶段，由 leader 对外发布，避免阶段倒退和错误的进度归属。
- 为已有 spill 告警补充内存 used／limit、维度、`m` 和 `ef_construction`。
- 生成阶段采样、参数、日志、内存近似值、索引大小和条件式建议报告。
- 第一版通过27个 HNSW TAP 文件／411个断言、4项 SQL regression；专项5个断言通过。

**当时的证据边界：**50k×64、两档内存、各三次的旧版受控对照没有观察到可分辨回归，但这是旧候选的小样本结果，不是今天整套诊断开销已经过关。采样得到的是观察到的时间跨度，短阶段可能漏掉。

证据：[环境基线](2026-09-02-mac-arm64-baseline.md)、[第一版实现与验证](2026-09-02-local-implementation-evaluation.md)。

### 阶段三：补 CentOS，并回到原始要求查漏｜9/3–9/4

**为什么调整：**你提出 OrbStack 可以直接创建 CentOS Machine；之后又要求重新核对谢灿扬的要求，不能只完成“能看到 spill”就宣布整个项目二完成。

**实际完成：**

- 为低召回补精确 Top-K 与 HNSW Top-K 的对照、查询计划校验和服务器执行时间。
- 完成14次50k×64参数实验，以及行数、维度、`m` 三条控制变量共10个独立规模点，最高实际达到1M×64。
- 整理异常证据，区分上游已有测试与本项目新增断言；没有为了测试主动制造宿主 OOM。

**重要修正：**最初候选只完整覆盖构建慢／spill／进度这一部分；召回、完整参数建议和规模证据是随后补齐的。1M 最终采用的247.056s来自统一采样后的记录，不把早期不同采样结果混用。CentOS只证明兼容性，不与Debian耗时拼成性能结论。

证据：[需求逐项复核](2026-09-03-requirements-progress-audit.md)、[CentOS兼容性](2026-09-03-centos-stream9-arm64-compatibility.md)、[参数诊断](2026-09-03-hnsw-parameter-diagnostics.md)、[规模验证](2026-09-03-hnsw-memory-scale.md)。

### 阶段四：从“采样看见阶段”到“内部记录阶段耗时”｜9/5–9/6

**为什么追加：**第一版轮询可能漏掉很短的阶段，无法可靠回答“到底耗时在哪一段”。经授权增加内部计时，而不是把采样跨度包装成精确耗时。

**实际完成：**新增默认关闭的 `hnsw.build_timing`，在内部构建调用中记录初始化、内存构建、spill 排空等待、图写入、落盘插入、收尾、WAL 和清理八段时间；处理并行共享数据生命周期，并把摘要接入报告。

新增049计时测试221个断言；Debian／CentOS各通过28个HNSW TAP文件、632个断言和4项SQL。工具45项测试、9个真实成功／失败／取消用例通过。

**没有完成的部分：**36次独立筛查及另40次配对计时已经运行，但不能建立稳定的低开销结论。内部时间是定位区间的证据，不等于完整SQL事务耗时，也不直接证明CPU或SSD是根因。

此后至9/13，C／TAP候选保持9/6版本。后续主要变化在工具、案例、验证方法和文档，不是每天都在重写HNSW。

证据：[内部计时实现与验收](2026-09-05-hnsw-build-timing.md)。

## 6. 汇报时最值得讲的两个案例

### 案例一：不是只说“spill很慢”，而是指出慢在哪、怎样验证调整

在同一份全量GloVe、固定 `m=16`、`ef_construction=64`、实际2个worker的条件下，每档独立构建三次：

| 构建内存预算 | spill | 完整构建时间中位数 | 三次范围 |
|---|---|---:|---:|
| 1024MB | 3/3 | 1414.649s，约23.6分钟 | 1114.468–1730.185s |
| 1792MB | 0/3 | 326.571s，约5.4分钟 | 315.599–538.041s |

低内存三次中，spill后的 `disk_insert` 分别占内部时间的69.4%、76.8%、79.7%；一次性 `flush` 分别只有6.367s、3.874s、12.576s。报告帮助区分了“把已有图写成页”和“之后继续处理剩余向量”这两件事。

在有资源余量的本地条件下，提高预算消除了spill，构建中位时间减少约76.9%；同时容器近似峰值中位数由2781.1MiB提高到3580.7MiB。

**能讲的价值：**诊断把“慢”收敛到具体构建路径，并提供了可复验的内存调整依据。

**不能讲成：**补丁让HNSW算法提速4.33倍、降低76.9%的生产成本，或已经证明SSD是根因。收益来自参数调整；诊断提供的是发现和验证依据。

原始结果和图：[构建内存案例](../experiments/hnsw_build/results/20260909T135759Z-glove-formal-cases/report.md)。

### 案例二：索引能查，不代表召回合格；提高召回也不是免费的

首轮GloVe在既定搜索上限下未达到目标，因此另经授权开展有限的新选参轮次，而不是改写旧结果。新轮最终选择 `m=16 / ef_construction=128 / ef_search=1000`，并锁定后使用新的1000个验证查询。

在同一个最终索引上比较：

| ef_search | 验证平均Recall@10 | 暖缓存服务器查询p50 | p95 |
|---:|---:|---:|---:|
| 400 | 91.13% | 3.740ms | 7.127ms |
| 1000 | 95.47% | 28.998ms | 44.945ms |

召回增加4.34个百分点，但查询中位耗时约为原来的7.75倍。95.47%是这1000个查询上的平均值，不保证每个查询达到95%，也不是业务最优参数；当前没有业务延迟预算。

**能讲的价值：**工具同时揭示质量问题和解决它的成本，让使用者按业务要求做选择。

**不能讲成：**我们改进了HNSW搜索算法、无代价提高召回，或已经证明RAG回答更准确。也不能用新旧两轮不同索引、不同验证集的数字直接做因果比较。

原始结果和图：[有限召回改进](../experiments/hnsw_build/results/20260910T074253Z-bounded-recall/report.md)。

已有任务观察器可以作为这两个案例之外的一个短演示：用受限账号展示中途接入、等待状态与任务消失后的“不确定”。它证明工具不再只能观察自己启动的实验，但仍不是生产接入成功的证据。

## 8. 哪些细化必要，哪里应该收住

### 有明确价值的细化

- 从“有进度”到“能区分构建路径”：解决真实的信息不足。
- 从轮询跨度到内部计时：补上短阶段漏采，而不是增加装饰性图表。
- 从合成数据到公开GloVe：增加非合成向量上的使用证据。
- 从实验工具到已有任务只读观察：补上实际使用方式。
- 从单看召回到同时报告延迟：防止建议只有收益、没有代价。
- 从“测完了”到核对实验公平性：发现旧开销对照存在混杂，避免错误归因。

### 需要明确收口的地方

截至旧A/A阶段，多轮开销验证仍未形成正式的新旧性能结论。9/13的完整新对照已将未建立支持的条件收敛到三项并行场景，但整体性能仍未验收。它是交付质量问题，不应吞掉整个项目的业务主线，也不应靠继续换环境或重复抽样碰到通过。

旧A/A的额外准入条件，在每场景8个配对时，实际上要求全部配对的绝对差异不超过10%；这与“诊断相对原版的总体中位成本上界低于5%”不是同一个问题。本轮已完成方法审查并另立固定协议；旧条件和失败仍保留，没有删掉条件后宣称原协议通过。

早期文档多次写“完成”，后来又继续增强，容易让你混淆。更准确的记录方式应是：**9/4第一版范围完成；9/6新增计时功能验证完成；9/10案例与观察工具完成；当前整体性能验收和交付未完成。**完成必须带版本和范围，不能用某份旧报告的状态覆盖整个项目。
