# 并行 HNSW 工作量与 CPU 机制诊断

这是 9 月 13 日继续开发的独立诊断，开始前固定范围。不是新的 5% 验收，不合并此前样本，不修改 9 月 12 日冻结协议及其 9/12 支持、3/12 未建立支持的结论。5% 仍是项目内自设参考线。

## 动机与问题

已完成的 768 次正式测量及 384 次预热中，三个并行比较仍未建立低于 5% 的支持。离线检查全部日志发现：

- 并行同条件重复的 SQL 时间变化与 cgroup CPU 时间变化高度同步，单纯离开 CPU 等待不能充分解释波动。但工作量、执行速度和内存停顿尚未区分。
- `HNSW_MEMORY` 的 seed42 只在 leader 初始化；并行 worker 的随机层数及并发建图顺序仍会变化。
- 4 MiB 并行场景先扣除 3 MiB 共享区预留，剩余 1 MiB 恰好触及并行分配安全余量。因此所有并行 spill 日志都在 0 tuples 处落盘，测到的是从空图直接磁盘插入。

本轮直接询问：耗时波动是否伴随距离计算次数变化？CPU 时间与距离计算数的关系如何？真正经过内存建图后再 spill 的场景是否可正常观测？不从相关性直接归因于候选 C 缺陷。

## 隔离插桩

从同一 v0.8.6 源码归档分别产生原版和既有候选，用此前已锁定的编译器与运行时本地镜像构建。候选工作区不修改。插桩生成器、两个补丁、源文件摘要、完整插桩源码归档、构建日志与二进制身份单独保存。

保留原来的 leader seed42 与 native worker 随机流；不替换层数算法，不固定 worker 插入顺序，不增加共享计数器。只在隔离源码里加入进程本地计数：距离函数调用数、初始化元素数、64 桶层数直方图、扫描回调数、成功插入数。扫描前后各采集一次进程用户/系统 CPU 时间及 elapsed 时间。每个参与进程成功结束扫描后输出一次单行 JSON NOTICE。

所有指标限定 `scan_and_insert`：包含扫描期间的 spill，但不包含 leader 扫描完成后的最终 flush、WAL 与清理。整条 CREATE INDEX SQL 耗时另行保留。三个进程的 CPU 可以相加，elapsed 不能相加。直方图记录初始化候选元素，通常不等于任意业务数据的最终图节点数；本轮非空无重复合成数据应与行数一致。

插桩本身会增加本地计数与日志成本，并可能改变调度。它只能帮助解释机制，不能以“每次距离调用时间”或移除波动后的数据宣称原候选总体低于 5%。

## 固定范围

先独立运行 9 次流程预检：三个条件 × 三个场景各一次，验证编译、记录覆盖与路径。预检结果不并入随后诊断。

正式诊断预算固定为 **54 次构建**：2 个全新面板 × 3 个条件 × 3 个场景 ×（1 次预热 + 2 次测量），共 36 次测量、18 次预热。条件为原版、候选 timing off、候选 timing on。此轮不增加观察器这一变量。

| 场景 | 行数 | maintenance_work_mem | 预期路径 |
|---|---:|---:|---|
| no-spill | 100,000 | 256 MiB | 内存构建，扫描结束后 flush |
| immediate-spill | 30,000 | 4 MiB | 0 tuples 时落盘 |
| partial-spill | 30,000 | 8 MiB | 插入部分向量后落盘，要求 0 < spill tuples < 30,000 |

共同设置：32 维、m=16、ef_construction=64、两个 worker 加 leader；合成数据生成与旧实验一致。每个面板三个隔离实例，各 2 GiB 内存、guest CPU 0–9；一次仅运行一个构建。前后检查 AC，使用进程范围内 caffeinate；civil/monotonic 差值超过 1 秒、记录不完整、路径不符或源码中途变化均使批次失败。

条件顺序用 seed 20260913 打乱六个排列，六个面板/场景块各使用一个排列及其反序。第二面板反转实例槽位和场景顺序。完整 schedule 在构建前写入 protocol.json。这个小设计只用于机制描述，不主张独立重复充分、消除所有漂移或统计检验有充足功效。

## 校验与报告

每次必须有 leader 与 worker 0/1 各一份记录，PID 唯一且 index OID 对应当次索引；三个进程合计回调、插入、初始化和直方图计数等于目标行数。记录所有层数、CPU、SQL 时间、内存、宿主负载、spill tuple 数、index bytes 和原始日志。全计划完成后才形成描述性报告，所有场景与条件均保留，不挑选异常值或较好重复。

首先比较每条件两次重复的 SQL 时间、进程 CPU 和距离计算数变化；随后描述层数分布、距离调用/行、CPU/距离调用，以及不同 spill 路径的差异。它们是解释性观测，不能证明因果、CPU 频率变化或 C 无回归。根据机制证据决定是否有必要修复实际代码问题，或另行制定新的前瞻性能验证；不按效果自动追加这一批样本。

只清理本任务 nonce 标记的实例与卷。提交、推送、PR、项目方联系继续留给完成开发后的用户安排。
